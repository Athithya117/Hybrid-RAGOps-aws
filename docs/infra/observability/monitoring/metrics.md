# Monitoring & Metrics — actual, observed state (revised)

## Simple summary (one-paragraph)

This document lists the production-grade metrics you must collect for a Retrieval-Augmented Generation (RAG) system, explains exactly what each metric means, and justifies why it is needed for operational reliability, observability, and capacity planning. It excludes alert rules — it focuses on measurement, labels, cardinality constraints, and practical queries you will use to validate pipeline health and correctness.

## Precise scope and goals

* **Scope:** vmagent (scraper), VictoriaMetrics (TSDB), retrieval service (retriever), and vector DB (Qdrant).
* **Goals:** ensure requests succeed, responses are timely and relevant, vector DB is healthy, ingestion pipeline (scrape → remote-write → TSDB) is intact, and resource/cost signals are available for capacity and cost-control decisions.
* **Constraints:** low cardinality by default; strong guardrails on dynamic labels; metrics must be Prometheus-format and exposed on `/metrics`.

---

# 1. High-level metric categories and why they matter for RAG

1. **Availability & readiness (service-level)**
   *Why:* RAG depends on multiple services (retriever, re-ranker, vector DB, LLM connectors). Knowing whether each service is healthy is the first gating factor for functionality.
   *Primary signal:* `service_ready{service="<name>",env="<env>"} 1|0`

2. **Request-level telemetry (throughput, errors, latencies)**
   *Why:* RAG correctness and UX depend on the retrieval step being fast and correct. Latency drives user response time; errors drive user-visible failures and can indicate regressions in connectors (Qdrant, LLM).
   *Primary signals:* `retrieval_requests_total`, `retrieval_errors_total`, `retrieval_request_duration_seconds` (histogram).

3. **Vector DB (Qdrant) domain metrics**
   *Why:* Vector DB is a core dependency; collection counts, vector counts, cluster health and request latency determine retrieval relevance and scale.
   *Primary signals:* `collections_total`, `collections_vector_total`, `qdrant_query_total`, `qdrant_query_duration_seconds`, `cluster_peers_total`, `cluster_term`, `cluster_commit`.

4. **Pipeline observability (scrape & ingestion)**
   *Why:* A failing scrape or remote-write does not show up immediately in `up{}`; you need vmagent-level metrics and Victoria ingest counters to confirm data made it into the TSDB.
   *Primary signals:* `vm_promscrape_*` family (discovery, scrape counts), `vm_persistentqueue_bytes_written_total`, `vm_promscrape_conn_bytes_written_total`, Victoria query `seriesFetched` in PromQL responses.

5. **Resource & process metrics**
   *Why:* CPU/memory, file descriptors, open mmaps, and persistent queue sizes help prevent OOMs / file descriptor exhaustion and show ingestion backpressure.
   *Primary signals:* `process_resident_memory_bytes`, `process_virtual_memory_bytes`, `process_open_fds`, `vm_persistentqueue_bytes_pending`.

6. **Application-level business signals (retrieval quality / volume)**
   *Why:* These metrics show whether retrieval is being used and with what shape (documents returned, reranker timings, LLM calls), useful for capacity planning and cost attribution.
   *Primary signals:* `retrieved_docs_count` (histogram), `rerank_duration_seconds`, `llm_calls_total`, `presign_requests_total`.

# 2. Exact metrics (names, type, and precise rationale)

> For each metric below: **name** — *type* — **why required for RAG** — **label guidance**.

---

## A. Retrieval service (retriever)

* `retrieval_requests_total` — *counter*
  **Why:** global throughput; baseline for cost and scaling decisions.
  **Labels:** `service`, `env`, `endpoint` (keep `endpoint` coarse; do not include query text).

* `retrieval_errors_total` — *counter*
  **Why:** indicates failed retrievals (upstream errors, timeouts, bad inputs). Use with `retrieval_requests_total` to calculate error rate.
  **Labels:** `service`, `env`, `error_type` (bounded set).

* `retrieval_request_duration_seconds` — *histogram* (use standard buckets appropriate for user-visible latency — e.g., `[.005,.01,.025,.05,.1,.25,.5,1,2.5,5,10]`)
  **Why:** P95/P99 latency drives UX; histograms required to compute percentiles.
  **Labels:** `service`, `env`, `endpoint`, `status_code` (avoid high-cardinality labels).

* `retrieved_docs_count` — *histogram* (bounded)
  **Why:** indicates result set sizes; can detect regressions where too many or too few docs are returned, which impacts LLM cost and relevance.

* `qdrant_query_total` — *counter*
  **Why:** shows number of vector DB queries generated by retriever (attribution of DB calls).
  **Labels:** `service`, `env`, `method` (e.g., `search`, `lookup`).

* `qdrant_query_duration_seconds` — *histogram*
  **Why:** vector DB latency influences retrieval latency and overall SLA.

* `dense_embed_requests_total`, `sparse_embed_requests_total` — *counters*
  **Why:** tokenizes calls to embedding services (cost attribution and throughput scaling).

* `llm_calls_total`, `llm_call_duration_seconds` — *counter* and *histogram*
  **Why:** LLM invocations are the dominant cost; these metrics are required for cost accounting and to detect unexpected invocation spikes.

* `service_ready` — *gauge* (0/1)
  **Why:** readiness gating for traffic shaping (used in tests and orchestration).

**Notes:** Keep retriever labels minimal: `service`, `env`, `status_code`, and `endpoint` with a very limited set (no user IDs, request IDs, or query text).

---

## B. Qdrant (vector DB)

* `app_info{name="qdrant",version="<x>"}` — *gauge* (static)
  **Why:** confirms binary version and build, used during rollbacks/compatibility checks.

* `collections_total` — *gauge*
  **Why:** count of collections; increases when data is created/seeded and used in health checks.

* `collections_vector_total` — *gauge*
  **Why:** total number of vectors stored; used to validate ingestion pipelines (if you seed vectors for tests, this should increase).

* `collection_active_replicas_min` / `_max` — *gauges*
  **Why:** verify replica distribution and data redundancy.

* `qdrant_query_total` — *counter* (Qdrant-side)
  **Why:** DB-level request volume; helps differentiate application-side retries vs DB-level load.

* `qdrant_query_duration_seconds` — *histogram*
  **Why:** DB latency distribution; critical to measure tail latency for relevance and SLA.

* `cluster_peers_total`, `cluster_term`, `cluster_commit`, `cluster_pending_operations_total` — *gauges/counters*
  **Why:** cluster health and raft/consensus stability. If `cluster_peers_total` drops or `cluster_pending_operations_total` grows, consistency or availability issues may follow.

* `memory_*` (resident, active, allocated) & `process_open_fds` — *gauges*
  **Why:** resource metrics to prevent OOM or FD exhaustion which cause degraded performance.

**Label guidance:** minimal or none for collection-level counts; when adding labels, limit to `namespace` and `collection` (only if collection count is low and cardinality controlled).

---

## C. vmagent / scrape & ingestion pipeline (vmagent metrics)

* `vm_promscrape_config_last_reload_successful` — *gauge*
  **Why:** indicates config errors in scrape config; if reload fails, no new targets will be discovered.

* `vm_promscrape_discovery_kubernetes_objects{role="pod"}` — *gauge*
  **Why:** shows how many pod objects the scraper sees; zero means discovery failed (RBAC or API issues).

* `vm_promscrape_scrape_pool_targets{scrape_job="<job>",status="<up|down>"}` — *gauge*
  **Why:** direct per-job target status (e.g., `k8s-pods-qdrant`, `k8s-pods-retriever`). Use to confirm vmagent sees intended jobs.

* `vm_promscrape_scraped_samples_sum` / `_count` — *counters/histogram*
  **Why:** number of samples scraped; should be greater than zero for active jobs.

* `vm_promscrape_conn_bytes_written_total` / `vm_persistentqueue_bytes_written_total` — *counters*
  **Why:** indicates remote-write bytes sent or queued to Victoria. Primary proof vmagent is transmitting data.

* `vm_persistentqueue_bytes_pending` — *gauge*
  **Why:** shows backpressure; if pending grows it may indicate remote write problems or network issues.

* `vm_log_messages_total{level="error",location=...}` — *counter*
  **Why:** counts agent errors (useful immediately to detect RBAC `pods is forbidden` errors or other discovery failures).

**Why these vmagent metrics are essential for RAG:** they provide the authoritative evidence that service metrics were scraped and forwarded to the TSDB. Tests and operational checks should use these metrics before trusting PromQL results.

---

## D. Victoria (TSDB internal / query signals)

* `vm_http_requests_total{path="/api/v1/query"}` — *counter*
  **Why:** query traffic to Victoria (useful to see test and dashboard patterns).

* `vm_filestream_real_written_bytes_total`, `vm_filestream_buffered_written_bytes_total` — *counters*
  **Why:** correlate writes with vmagent remote-write bytes; ensure TSDB is persisting.

* **PromQL query metadata:** `seriesFetched` in PromQL response stats (not a metric name — returned by VM query API)
  **Why:** `seriesFetched` in the HTTP response is the most direct proof that Victoria returned non-empty result sets to PromQL queries. Tests should inspect this field.

# 3. Practical PromQL checks & examples (for operational use and tests)

> These are the canonical queries used by the test harness and should be considered standard health checks.

1. **Check retrieval metrics exist in TSDB**

   ```promql
   count({__name__=~"app_info|retrieval_requests_total|retrieval_errors_total"})
   ```

   *Expected:* `> 0`. If `0`, either scrape/remote-write failed, or retriever not instrumented/exposed.

2. **Check qdrant metrics exist in TSDB**

   ```promql
   count({__name__=~"app_info|collections_total|collections_vector_total"})
   ```

   *Expected:* `> 0`. Matches presence of Qdrant metrics.

3. **Check vmagent remote-write activity**

   ```promql
   sum(vm_persistentqueue_bytes_written_total) or sum(vm_promscrape_conn_bytes_written_total)
   ```

   *Expected:* increases over time when scrapes occur.

4. **Check namespace-level presence (observational)**

   ```promql
   max(up{namespace="inference"})
   max(up{namespace="qdrant"})
   ```

   *Note:* `up` can be empty or non-authoritative. Use it as a secondary signal only.

5. **Query Victoria and inspect `seriesFetched`**
   The test harness should call:

   ```
   GET /api/v1/query?query=<expr>
   ```

   then inspect `.stats.seriesFetched` in the JSON response. `seriesFetched > 0` is actionable proof that Victoria has series for the given expression.

# 4. Labeling and cardinality rules (exact guidance)

* Allowed static labels: `service`, `env`, `endpoint`, `status_code` (bounded set).
* Forbidden/avoid: any per-request identifiers (user IDs, query text, session IDs), high-cardinality fields (document IDs, query hashes).
* When exposing collection-level metrics for Qdrant, only include `collection` label if number of collections is very small and bounded (e.g., dev/test). Prefer aggregate metrics without collection label in prod to avoid cardinality explosion.
* Histograms: use bounded, fixed buckets. Do not create custom unbounded buckets per request.

---

# 5. Instrumentation best practices (practical, exact)

* Use stable metric names; follow Prometheus naming conventions (`<component>_<operation>_<unit>[_total|_seconds]`).
* Counter semantics: always monotonic; never reset except on process restart. Use monotonic counters for rates.
* Histogram buckets: choose boundaries that capture P50/P95/P99 and the tail relevant to user SLAs. Example buckets for retrieval request latency: `[0.005,0.01,0.025,0.05,0.1,0.25,0.5,1,2.5,5,10]`.
* Expose readiness (`/readyz`) and liveness (`/healthz`) endpoints; expose `service_ready` gauge to reflect readiness state for monitoring.
* Ensure `/metrics` responds quickly and does not trigger expensive work (avoid in-metrics heavy DB queries).

# 6. Test harness behavior & troubleshooting checklist (exact steps)

If tests report “empty TSDB”:

1. **Check vmagent logs** for RBAC / discovery errors (e.g., `pods is forbidden`); if present, ensure vmagent ServiceAccount has cluster-scoped `list/watch` permissions for `pods,endpoints,services,nodes`.
2. **Confirm vmagent sees pods:** query local vmagent `/metrics` for `vm_promscrape_discovery_kubernetes_objects{role="pod"}` > 0.
3. **Confirm target up metrics:** `vm_promscrape_scrape_pool_targets{scrape_job="k8s-pods-retriever",status="up"} > 0`.
4. **Confirm remote-write bytes:** `vm_persistentqueue_bytes_written_total > 0` or `vm_promscrape_conn_bytes_written_total > 0`.
5. **Query Victoria and inspect `seriesFetched`:** run the same PromQL used by tests and verify `.stats.seriesFetched` > 0 in the query response.
6. **If PromQL returns `result: []` but vmagent shows scrapes:** check for `seriesFetched` vs `result` mismatch; ensure test harness parses raw JSON (no colorized `jq -C`) and does not reformat the response before parsing. Use `jq -c` (compact) or raw `curl` then `jq` on it.

# 7. Retention, cardinality and cost considerations (practical)

* **Retention:** dev/test: `1d` is sufficient; prod: set retention per business requirements (30d, 90d). Longer retention means higher storage cost, and more series retention.
* **Sampling and labels:** avoid per-request labels to reduce series churn. Use aggregated labels that help troubleshoot (e.g., `service`, `env`).
* **Histogram cardinality:** histograms create metrics per label combination; keep label set small to limit series multiplication.

---

# 8. Minimal instrumentation checklist to ship for RAG (deployable order)

1. Retriver: `retrieval_requests_total`, `retrieval_errors_total`, `retrieval_request_duration_seconds` (histogram), `service_ready`.
2. Qdrant: enable built-in metrics (`collections_total`, `collections_vector_total`, `qdrant_query_total`, `qdrant_query_duration_seconds`, cluster metrics).
3. vmagent: ensure ServiceAccount + ClusterRole + ClusterRoleBinding exist and are applied. Add `vmagent` persistent queue monitoring (`vm_persistentqueue_*`).
4. Victoria: ensure query API reachable and tests check `.stats.seriesFetched`.
5. Business signals: `retrieved_docs_count`, `llm_calls_total`.

# 9. Example minimal PromQL snippets for dashboards / tests

* Retriever requests per second:

  ```promql
  rate(retrieval_requests_total[1m])
  ```

* Retriever P95 latency:

  ```promql
  histogram_quantile(0.95, sum(rate(retrieval_request_duration_seconds_bucket[5m])) by (le))
  ```

* Qdrant query latency P99:

  ```promql
  histogram_quantile(0.99, sum(rate(qdrant_query_duration_seconds_bucket[5m])) by (le))
  ```

* Victoria ingestion bytes (agent → VM):

  ```promql
  increase(vm_persistentqueue_bytes_written_total[5m])
  ```

* Series presence check (test):

  ```promql
  count({__name__=~"app_info|collections_total|collections_vector_total"})
  ```

---

# 10. Closing notes (practical rationale)

* RAG systems are composite: availability of retrieval and vector DB, plus low tail latency, determine perceived quality. Metrics must measure both **business-level signals** (requests, docs returned, LLM calls) and **pipeline-level signals** (scrapes, remote-write, TSDB ingestion).
* vmagent metrics + Victoria `seriesFetched` are the authoritative proof of observability pipeline integrity. If either is missing, PromQL-based checks are unreliable.
