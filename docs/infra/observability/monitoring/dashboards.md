# Platform Dashboards — Deterministic, Service-Centric Views (retriever, qdrant, ingestion)

---

## Purpose

This document specifies the canonical, deterministic Grafana dashboard designs for the platform. Each dashboard is generated by the platform generator, uses fixed variables, links into ClickHouse logs deterministically, and relies on the exact metric and log schema enforced by Vector → ClickHouse. Dashboards are diagnostic surfaces only; they do not trigger paging. All dashboards and panels are immutable except via the generator.

---

## Global rules & conventions (must be enforced by generator and CI)

* **Single generator source**: dashboards are generated only by `infra/generators/monitoring_and_alerts.sh`. Manual edits to rendered dashboards are rejected.
* **Canonical variables (required on every dashboard)**:

  * `$service` — logical service name (e.g., `retriever`, `qdrant`, `vmagent`)
  * `$namespace` — Kubernetes namespace
  * `$pod` — (optional) pod name
  * `$__from`, `$__to` — Grafana time range variables
* **Top-left metadata panel**: owner, escalation channel, runbook URL, and currently applied SLO env var values (rendered into text).
* **One canonical dashboard per service** (e.g., `Service Overview — retriever`, `Service Overview — qdrant`) and one `Ingestion Health` dashboard.
* **All panels must include** a “Logs” data link that opens Grafana Explore prefilled with the canonical ClickHouse SQL and the exact time range.
* **Panel resolution**:

  * SLO/latency panels: 1m / 5m resolution (PromQL using `rate(...[5m])`).
  * Long-term trend panels: 1h resolution.
* **Dashboards stored in repo**: generator produces JSON or provisioning YAML; CI validates presence and variable bindings.

## ClickHouse log Explore SQL template (deterministic)

Use this single SQL template for all panels’ Logs link. It must be injected verbatim by the generator and use Grafana variables.

```sql
SELECT
  ts,
  level,
  message,
  service,
  namespace,
  pod,
  trace_id,
  fields
FROM logs.kube_logs
WHERE service = '$service'
  AND namespace = '$namespace'
  AND ts BETWEEN toDateTime64($__from / 1000, 3) AND toDateTime64($__to / 1000, 3)
ORDER BY ts DESC
LIMIT 500
```

Grafana Explore link template (use exactly in Data link):

```
/explore?left={"datasource":"ClickHouse","queries":[{"refId":"A","sql":"<URL-encoded-SQL>"}],"range":{"from":"$__from","to":"$__to"}}
```

(generator must URL-encode the SQL when injecting into the dashboard JSON).

## Dashboard: Service Overview — retriever

### Purpose

One-page diagnostic view for retriever: SLO status, error-rate, latency, throughput, readiness, downstream Qdrant usage, and direct links to logs and traces.

### Variables

* `$service` = `retriever` (default)
* `$namespace` (default `inference` or provided)
* `$pod` (optional)

### Panels (top-to-bottom)

1. **Header / Metadata**

   * Text panel showing: owner, PagerDuty/team, runbook link, SLO env var values (SLO_SUCCESS_TARGET, SLO_LATENCY_QUANTILE, RETRIEVER_LATENCY_THRESHOLD_SECONDS).

2. **SLO — Success Rate (single stat)**

   * PromQL:

     ```promql
     1 - (sum(rate(retrieval_errors_total[30d])) / sum(rate(retrieval_requests_total[30d])))
     ```
   * Display: gauge with target line at `${SLO_SUCCESS_TARGET}` (value injected for display).
   * Color: green >= target, yellow within 50% of error budget, red otherwise.
   * Data link: ClickHouse SQL template.

3. **Error Rate (time series)**

   * PromQL:

     ```promql
     sum(rate(retrieval_errors_total[5m])) / sum(rate(retrieval_requests_total[5m]))
     ```
   * Overlay: fast-burn threshold line computed from env vars:

     ```
     threshold_fast = (1 - SLO_SUCCESS_TARGET) * SLO_FAST_BURN_MULTIPLIER
     ```
   * Display: stacked area or line.

4. **P95 Latency (time series)**

   * PromQL:

     ```promql
     histogram_quantile(${SLO_LATENCY_QUANTILE}, sum(rate(retrieval_request_duration_seconds_bucket[5m])) by (le))
     ```
   * Threshold line: `${RETRIEVER_LATENCY_THRESHOLD_SECONDS}`.

5. **Request Rate (timeseries)**

   * PromQL:

     ```promql
     sum(rate(retrieval_requests_total[1m]))
     ```

6. **Qdrant usage from retriever (timeseries)**

   * PromQL:

     ```promql
     sum(rate(qdrant_query_total[5m]))
     ```
   * Context: shows downstream pressure.

7. **Service readiness (single stat)**

   * PromQL:

     ```promql
     avg(service_ready{service="retrieval"})
     ```
   * Behavior: 1 = ready, 0 = not ready. Data link: click to Kubernetes pod list.

8. **Logs (panel action)**

   * Data link: click to Explore with SQL template prefilled for `$service` & `$namespace`.

9. **Traces (optional)**

   * If `trace_id` is present in logs and traces are available, provide a data link template:

     ```
     https://tracing.company.internal/trace/$trace_id?from=$__from&to=$__to
     ```

### Recording rules (recommended)

Create recording rules to reduce eval cost and stabilize display:

* `job:retrieval_error_rate:5m = sum(rate(retrieval_errors_total[5m])) / sum(rate(retrieval_requests_total[5m]))`
* `job:retrieval_p95_latency:5m = histogram_quantile(0.95, sum(rate(retrieval_request_duration_seconds_bucket[5m])) by (le))`

Generator must ensure recording rules exist in `monitoring/recording_rules.yaml`.

## Dashboard: Service Overview — qdrant

### Purpose

Show Qdrant collection health, queries, latency, cluster metrics, and direct log links.

### Variables

* `$service` = `qdrant` (default)
* `$namespace`
* `$pod` (optional)
* `$collection` (optional; only if cardinality is known and small)

### Panels

1. **Header / Metadata** (owner, runbook, SLO env vars for qdrant)
2. **Collections total (single stat)**

   * PromQL:

     ```promql
     collections_total
     ```
3. **Vectors total (single stat)**

   * PromQL:

     ```promql
     collections_vector_total
     ```
4. **Qdrant queries/sec**

   * PromQL:

     ```promql
     sum(rate(qdrant_query_total[1m]))
     ```
5. **P95 Query Latency**

   * PromQL:

     ```promql
     histogram_quantile(0.95, sum(rate(qdrant_query_duration_seconds_bucket[5m])) by (le))
     ```
   * Threshold line: `${QDRANT_LATENCY_THRESHOLD_SECONDS}`
6. **Cluster peers / pending operations**

   * PromQL:

     ```promql
     cluster_peers_total
     cluster_pending_operations_total
     ```
7. **Dead replicas (single stat)**

   * PromQL:

     ```promql
     max(collection_dead_replicas)
     ```
   * If > 0, highlight red and link to runbook.
8. **Logs (panel action)** — ClickHouse SQL template.

## Dashboard: Ingestion Health

### Purpose

Authoritative view for vmagent → Victoria pipeline. Used by platform and CI smoke tests.

### Variables

* `$namespace` (monitoring)
* `$vmagent` (pod selector)

### Panels (top-to-bottom)

1. **vmagent discovery (time series)**

   * PromQL:

     ```promql
     vm_promscrape_discovery_kubernetes_objects{role="pod"}
     ```
   * Alert hint: if equals `0` for >2m, ingestion-plane alert fires.

2. **vmagent remote-write bytes (increase over 5m)**

   * PromQL:

     ```promql
     increase(vm_persistentqueue_bytes_written_total[5m])
     ```

3. **vmagent pending queue**

   * PromQL:

     ```promql
     vm_persistentqueue_bytes_pending
     ```

4. **Scrape pool target status (per job)**

   * PromQL:

     ```promql
     vm_promscrape_scrape_pool_targets{status="up"}
     ```
   * Show per job: `k8s-pods-retriever`, `k8s-pods-qdrant`

5. **Victoria query diagnostic**

   * Implementation note: this panel uses a backend script or data link that calls Victoria `/api/v1/query?query=count(retrieval_requests_total)` and displays `.stats.seriesFetched`. The panel should show `seriesFetched` and last successful timestamp.
   * Generator must provide a small backend check job used by CI and dashboard.

6. **Logs (panel action)** — ClickHouse SQL template for `service=vmagent` or namespace `monitoring`.

## Dashboard: Platform Overview (single-screen MTTD)

Panels:

* Total ingestion health (composite)
* Number of services with `service_ready == 0`
* Total SLO burners (fast-burn currently firing)

  * PromQL:

    ```promql
    count(firing_alerts{plane="slo", severity="critical"})
    ```
  * Note: `firing_alerts` can be a recording rule populated from Alertmanager or vmalert metrics.
* Top 5 services by error-rate (5m)
* Click to `Service Overview` for each service

## Generator responsibilities (exact)

* Populate dashboard JSON with required variables and top-left metadata.
* Inject SLO env var values into header panel for deterministic display.
* URL-encode ClickHouse SQL when inserting Explore data links.
* Add panel `links` entries for Logs and Traces with variables `$service`, `$namespace`, `$pod`, `$__from`, `$__to`.
* Ensure all dashboards include a “how to silence” quick link to the runbook (runbook URL must be present).
* Keep dashboards under `monitoring/dashboards/` in repo; generator updates rendered JSON and CI validates.

---

## CI checks for dashboards (deterministic)

* **Rendering check**: generator produces dashboard JSON; artifact attached to PR.
* **Variable presence check**: CI lints JSON to assert `$service`, `$namespace`, `$pod` are declared.
* **SQL injection check**: ClickHouse SQL template must match canonical template; reject any deviation.
* **Link encoding check**: Data links must contain URL-encoded SQL.
* **Panel count & top-left metadata**: enforce minimal structure (>=5 panels, header present).
* **Permissions**: dashboards must be provisioned read-only for non-platform-engineers (set in Grafana provisioning).

---

## Best practices for authors of new panels

* Do not create new dashboards without a PR to the generator.
* Build panels using recorded rules when possible to reduce query cost.
* Keep label cardinality low on panels; aggregate across labels in dashboards rather than creating one panel per unique label.
* Use the canonical ClickHouse SQL template for logs; do not write custom SQL in panel links.
* Add runbook link and owner in the header before creating new dashboards.

## Retention & temporal resolution guidance

* SLO short-windows: use 5m/1m evaluation windows for alerting dashboards (and vmalert rules).
* Long-term trend panels: 30d retention resolution; sampling at 1h for panels.
* ClickHouse logs retention and TTL must be documented separately; dashboards assume `ts` millisecond accuracy.

---

## Operational notes

* If dashboards show empty data while pod metrics appear in `/metrics`, verify ingestion dashboard first (vmagent panels + Victoria seriesFetched).
* Use the ingestion dashboard’s Victoria diagnostic panel as the authoritative check for CI smoke tests.
* For traceability, the dashboard JSON used by Grafana must be stored and tracked in Git; generator changes must be code-reviewed.

---

## Deployment checklist (copyable)

1. Add/modify dashboard templates in `monitoring/dashboards/templates/`.
2. Run generator: `infra/generators/monitoring_and_alerts.sh` to render dashboards.
3. CI: validate variable presence, check SQL template adherence, attach rendered dashboard artifact.
4. Provision dashboards to Grafana via provisioning config or API.
5. Validate in staging: open Service Overview for retriever and verify panels show metrics and logs link opens Explore with results.
6. Promote to prod following platform promotion policy.
